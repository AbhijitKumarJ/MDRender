Response#

The Graph Engineering Manifesto#

Part 7: W3C PROV-O: Cryptographic Provenance for AI Decisions#

In [Part 6], we explored why naive RAG fails in the enterprise. We replaced fuzzy vector similarity searches with a rigid Knowledge Graph (ortho-knowledge-graph) and implemented our first layer of defense: the Ontology Gate. By defining strict SHACL-style schemas, we mathematically prevented the LLM from inventing illogical relationships.

But the Ontology Gate only checks the shape of the data. It ensures that [Patient] -> (ENROLLED_IN) -> [Trial] is grammatically correct within our business logic.

It does not check if the statement is actually true.

LLMs are notorious for "hallucinating" highly plausible, perfectly formatted lies. An agent might confidently assert that Patient P-001 is enrolled in the trial, simply because that outcome aligns with its training data or the surrounding context.

If you are auditing clinical trials, executing financial trades, or managing legal discovery, you cannot rely on an LLM promising that a fact is real. You need cryptographic proof.

The Provenance Crisis#

In standard agentic frameworks, data ingestion looks like this:

  1. The agent reads a PDF.
  2. The agent generates a summary or extracts an entity.
  3. The extracted data is pushed into a database.

At step 3, the connection to reality is severed. The database holds a fact (Patient P-001 is Enrolled), but it has absolutely no idea where that fact came from.

When a human auditor inevitably asks, "Why did the AI system conclude Patient P-001 is enrolled?" the engineers have to shrug. They can't point to a specific page in a specific document; they can only point to a JSON blob that the LLM generated three weeks ago. This black-box ingestion pipeline is an immediate failure of compliance.

Enter W3C PROV-O#

To solve this, Orthograph OS implements the W3C PROV-O (Provenance Ontology) standard at the database kernel level.

PROV-O is a W3C specification designed to provide an interoperable framework for exchanging provenance information. It maps out the lineage of data by linking Entities (the data), Activities (the processes that created them), and Agents (the actors who executed the processes).

In Orthograph, a fact is never just a triplet. It is a four-dimensional object bound to an immutable lineage chain.

The Provenance Gate: Rejecting Hallucinations at the Kernel#

When the Executor agent calls the insert_fact MCP tool, providing the subject, relation, and object, the Orthograph kernel does not immediately save the data. It hits the Provenance Gate.

The prompt explicitly instructs the LLM: “You MUST supply a valid source_document_id. If you invent a fact, the Knowledge Graph will violently reject the transaction.”

But we don't trust the prompt. We enforce it in Python.

The LLM is mathematically barred from injecting data into the enterprise memory unless it can explicitly cite a document registered in the trusted corpus.

Cryptographic Lineage: The fact_hash#

Passing the Provenance Gate is just the first step. Next, Orthograph binds the fact to its origin using cryptographic hashes (SHA-256).

Every time a fact is committed, the system generates an immutable lineage chain representing the extraction event:

  1. Document: trial_data_v2.pdf
  2. SourceFragment: Hash of (Document ID + Chunk Index).
  3. Extraction: Hash of (Agent ID + Fragment ID + Timestamp + Confidence).
  4. Fact: Hash of (Subject + Relation + Object + Extraction Hash).
python 
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/provenance/tracker.py

def compute_fact_hash(
    subject: str, relation: str, obj: str, extraction_hash: str
) -> str:
    """Fingerprint of the committed triple bound to its extraction."""
    joined = f"{subject}|{relation}|{obj}|{extraction_hash}"
    return f"hash-{hashlib.sha256(joined.encode('utf-8')).hexdigest()[:24]}"

This creates an unbreakable, machine-auditable chain.

If you look at Fact-104 in the database, its fact_hash contains the extraction_hash, which contains the fragment_id. You can trace the fact back to the exact millisecond it was extracted, the exact agent model that performed the extraction (claude-3-5-haiku), and the exact paragraph of the exact PDF it originated from.

If the underlying source document is ever updated or retracted, the system knows exactly which facts in the graph were derived from it and must be re-evaluated.

Conclusion#

By enforcing the Provenance Gate and generating cryptographic fact_hash chains, Orthograph OS completely eliminates data hallucination as an infrastructure risk.

The LLM might still occasionally try to invent a fact, but the graph database acts as an unyielding bouncer, demanding a valid receipt before opening the door. Accountability is baked into the math of the storage layer.

However, even if a fact is ontologically correct and backed by a real document, a problem remains. What happens when two perfectly valid, provenanced documents contradict each other?
