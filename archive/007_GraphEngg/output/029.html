The Graph Engineering Manifesto#

Part 8: The Fusion Gate: Time-Travel and Conflict Quarantine#

In [Part 6] and [Part 7], we built the first two defenses of our Semantic Memory layer (ortho-knowledge-graph). The Ontology Gate ensures that our agents can only extract relationships that exist in our business logic. The Provenance Gate ensures that every extracted fact carries a cryptographic receipt linking it to a trusted source document.

Together, these gates eliminate hallucination. But eliminating hallucination does not eliminate contradiction.

Enterprise data is messy and constantly changing. Consider the following scenario in our clinical trial database:

  • Document A (Processed Monday): "Patient P-001 is assigned to the Placebo Arm."
  • Document B (Processed Friday): "Patient P-001 has been reassigned to the Experimental Arm."

Both facts perfectly pass the Ontology Gate. Both facts have flawless cryptographic PROV-O lineage back to trusted documents.

How does a naive vector database (standard RAG) handle this? It simply stores both. When the agent asks, "Which arm is P-001 in?" the RAG pipeline pulls both contradictory chunks into the prompt, forcing the LLM to guess which one is right.

How does a standard SQL database handle this? It issues an UPDATE statement. It silently overwrites the old fact with the new fact, completely destroying the historical record.

Both approaches are unacceptable in Graph Engineering. We need a system that understands time, and we need a system that refuses to make autonomous decisions about conflicting truths. We need the Fusion Gate.

Understanding Functional Relations#

In our GraphSchema, we don't just define domain and range. We define mathematical constraints. One of the most important constraints is the functional flag.

python 
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/ontology/schema.py
schema.add_relation(
    "ASSIGNED_ARM", 
    domain="PatientRecord", 
    range="TrialArm", 
    functional=True  # <--- The critical flag
)

A functional relation means that a subject can only have one of these relationships at a time. A patient can report multiple adverse events (non-functional), but they can only be assigned to one trial arm.

When the Executor agent attempts to ingest Document B ([P-001] -> (ASSIGNED_ARM) -> [Experimental]), the kernel checks the database. It sees that [P-001] already has an ASSIGNED_ARM relationship.

Because the relation is marked functional=True, the transaction hits a hard stop.

Time-Travel: The Temporal Window#

But wait—patients are allowed to change trial arms over time. A functional conflict only occurs if two different facts are claimed to be true at the exact same time.

Orthograph solves this by implementing Temporal Knowledge Graphs. Every fact in the system supports a valid_from and valid_to half-open time window.

If the incoming fact from Document B specifies valid_from="2026-08-01", and the existing fact from Document A specifies valid_to="2026-07-31", there is no conflict. The graph accepts the new fact.

This enables powerful "Time-Travel" queries. The Supervisor agent can use the MCP tool query_graph_at(timestamp) to see the graph exactly as it existed on July 15th, completely blind to future events.

The Quarantine Queue#

But what happens if the dates do overlap? What if Document A and Document B both claim to be the definitive truth for the month of August?

In a lesser framework, the database would throw a fatal error, crashing the ingestion pipeline. In Orthograph OS, we use the Semantic Conflict Queue.

python 
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/fusion/resolver.py
class SemanticConflictQueue:
    def check_functional_violation(self, new_triplet, existing_triplets, is_functional):
        # ... logic checking for overlapping TimeWindows ...
        if new_window.overlaps(existing_window):
            self._quarantine_conflict(new_triplet, existing)
            return True
        return False

If the Fusion Gate detects an overlapping functional conflict, it does not commit the new fact to the graph, nor does it crash. It quarantines the attempted fact.

The insert_fact tool returns a typed, expected rejection to the Executor agent:

json 
{
  "status": "quarantined",
  "ok": false,
  "code": "FUSION_CONFLICT",
  "reason": "Fact conflicts with an existing functional relation in the graph."
}

The Executor agent (which runs on a fast clock and a cheap model) cannot resolve this. It lacks the capability. It registers the gap in its ledger.md and moves on to its next task.

Adjudication by the Supervisor#

This is where the Separation of Clocks (from Part 3) and Capability Security (from Part 11) shine.

Later, the Supervisor agent wakes up on its slow tick. It has the necessary supervisor role to access privileged MCP tools. It calls get_quarantined_conflicts() and sees the collision.

The Supervisor (running on a stronger reasoning model) retrieves the PROV-O lineage for both conflicting facts. It might discover that Document A is an informal email, while Document B is a signed clinical form.

The Supervisor then uses the resolve_conflict MCP tool:

json 
{
  "conflict_id": "CFL-4",
  "keep": "attempted",
  "actor": "supervisor"
}

The Python kernel receives this command, pops the conflict from the quarantine queue, explicitly logs the Supervisor's decision, and commits Document B's fact to the graph.

Conclusion#

By combining Temporal Windows with a Deterministic Quarantine Queue, we achieve a system that never loses historical data, never silently overwrites reality, and relies on strict, role-gated asynchronous adjudication to handle contradictions.

We have successfully built a Knowledge Graph that is structurally immune to hallucination, untracked sources, and semantic collisions.

But there is one final piece missing from our memory layer. We have stored the data. But how do we store the thought process of the agents themselves?

In Part 9: Decisions are Nodes: Making AI Reasoning Legally Auditable, we will explore "Decision Intelligence"—the practice of saving an LLM's logical conclusions as permanent, queryable graph nodes mathematically bound to the facts they cite.
