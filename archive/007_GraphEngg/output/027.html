The Graph Engineering Manifesto#

Part 6: Why Naive RAG is a Liability in Regulated Enterprises#

Up to this point in our series, we have focused entirely on execution. We built the Task Graph (ortho-task-graph), implementing independent clocks, durable markdown ledgers, and disjoint write-surfaces to ensure our agents work deterministically.

But flawless execution means nothing if the agent is operating on hallucinations. An efficient agent acting on bad data is just a machine for making mistakes faster.

In 2024, the tech industry thought it had solved the memory problem with RAG (Retrieval-Augmented Generation). The recipe was simple: chunk your PDFs into paragraphs, convert them to vector embeddings, store them in a database, and when the user asks a question, perform a cosine-similarity search to inject the most "relevant" text into the LLM's prompt.

If you are building a chatbot to summarize internal HR policies or help users troubleshoot a Wi-Fi router, naive RAG is fine.

If you are building autonomous agents for finance, healthcare, or defense, naive RAG is a catastrophic liability.

The Fundamental Mathematical Flaw of Vectors#

Let’s look at a concrete example in clinical trial management.

Imagine two documents are ingested into your RAG system:

  • Document A (Jan 2025): "Patient P-001 has been assigned to Trial Arm A (Placebo)."
  • Document B (June 2026): "Patient P-001 has been re-assigned to Trial Arm B (Experimental Drug)."

An autonomous agent, acting as a Clinical Trial Auditor, needs to determine if Patient P-001 should receive the experimental drug. It queries the vector database for "Patient P-001 Trial Arm."

How does a vector database resolve this? It doesn't.

Vector databases have no concept of time, logic, or entity identity. They only understand spatial geometry in high-dimensional space. The query returns both chunks of text because they are both mathematically similar to the query.

The RAG pipeline blindly dumps both contradictory statements into the LLM's prompt window:

Context 1: Patient P-001 is in Placebo. Context 2: Patient P-001 is in Experimental Drug.

The LLM is now forced to adjudicate a complex data conflict on the fly, inside the prompt window, using fuzzy probabilistic reasoning. Sometimes it picks Document A. Sometimes it picks Document B. Sometimes it hallucinates a "Trial Arm C" to split the difference.

If a human auditor asks, "Why did you give the experimental drug to a patient assigned to the placebo group?" the only answer you have is, "The cosine distance of the vector was 0.89."

In a regulated enterprise, under frameworks like the EU AI Act, HIPAA, or SOC 2, that answer results in massive fines, revoked licenses, or worse. You cannot deploy black-box probabilistic math for deterministic business rules.

From Similarity to Topology: The Knowledge Graph#

Graph Engineering demands a fundamentally different approach to memory. We must move from Vector Similarity to Topological Reality.

This is the purpose of the second half of Orthograph OS: ortho-knowledge-graph.

Instead of dumping unstructured text chunks into a database, Orthograph forces the LLM to extract highly structured RDF Triplets (Subject → Relation → Object).

Instead of storing: "Patient P-001 has been assigned to Trial Arm A"

The agent uses a strict MCP tool call (insert_fact) to store: [Patient: P-001] -> (ASSIGNED_ARM) -> [TrialArm: A]

This transforms language into mathematics. The database is no longer a search engine; it is a Topology.

The First Gate: Ontology Enforcement#

But simply extracting triplets isn't enough. LLMs are incredibly creative, which is exactly what we don't want when building a database schema.

If left unchecked, an LLM might extract: [Doctor: Smith] -> (MANUFACTURES) -> [Drug: Aspirin]

In a naive system, this hallucination is silently accepted. In Orthograph, it hits the Ontology Gate.

Before any fact is written to disk, the Orthograph kernel checks the proposed triplet against a strict, deterministic Python schema (which can compile down to W3C SHACL/OWL standards).

python 
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/ontology/schema.py
schema = GraphSchema(namespace="http://orthograph.local/clinical-trials#")

# Define the nodes
schema.add_node("Doctor", properties={"id": str})
schema.add_node("Drug", properties={"name": str})
schema.add_node("PharmaceuticalCompany", properties={"name": str})

# Define the STRICT rules of reality
schema.add_relation("PRESCRIBES", domain="Doctor", range="Drug")
schema.add_relation("MANUFACTURES", domain="PharmaceuticalCompany", range="Drug")

When the agent attempts to insert [Doctor] -> (MANUFACTURES) -> [Drug], the kernel executes a deterministic domain/range check. The database immediately throws an ONTOLOGY_VIOLATION error and rejects the transaction.

The LLM is mathematically barred from inventing relationships that do not exist in your business logic.

Conclusion#

Naive RAG assumes that if you throw enough text at an LLM, it will figure out the truth. Graph Engineering acknowledges that LLMs are stochastic text generators that must be bound by rigid data structures.

By moving from vectors to triplets, and enforcing strict ontological gates, we ensure that an agent's memory only contains structurally valid facts.

But ontological validity isn't enough. Just because a fact fits the schema doesn't mean it's actually true. What stops the LLM from inventing a perfectly formatted, schema-compliant lie?

In Part 7: W3C PROV-O: Cryptographic Provenance for AI Decisions, we will explore the second gate of the Orthograph Knowledge Graph. We will learn how to completely eliminate data hallucinations at the database level by requiring every single fact to carry a cryptographically secure receipt of its origin.
