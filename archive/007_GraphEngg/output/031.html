The Graph Engineering Manifesto#

Part 10: The Model Context Protocol (MCP) as the Ultimate Boundary#

In the first half of this series, we built the Task Graph (ortho-task-graph), a strict TypeScript orchestration engine that forces LLMs to obey deterministic rules. In the second half, we built the Knowledge Graph (ortho-knowledge-graph), a rigorous Python engine that prevents hallucinations using W3C PROV-O provenance and ontological gates.

We now have two brilliant, highly specialized systems written in different programming languages.

In 2024, if you wanted to connect a TypeScript agent to a Python data-science backend, you had to build a custom REST API. You had to define OpenAPI Swagger specs, write custom prompt wrappers to teach the LLM how to format JSON payloads, handle HTTP timeouts, and manually deserialize the responses. It was tedious, brittle, and tightly coupled the agent to the backend.

In 2026, we don't build custom APIs for agents. We use MCP.

What is the Model Context Protocol (MCP)?#

The Model Context Protocol (spearheaded by Anthropic) is an open standard that standardizes how AI models connect to data sources and tools.

Instead of teaching an LLM how to talk to fifty different custom APIs, you teach the LLM how to speak MCP. Then, any backend service can expose an "MCP Server." The agent automatically discovers the available tools, understands their JSON Schema requirements, and knows exactly how to invoke them.

In Orthograph OS, MCP is the load-bearing bridge between our fuzzy TypeScript agents and our rigid Python memory kernel.

The Architecture: FastMCP over Server-Sent Events (SSE)#

Orthograph implements this boundary using fastmcp (in Python) and the official @modelcontextprotocol/sdk (in TypeScript).

Here is how the architecture is wired:

text 
TypeScript (ortho-task-graph) 
       │
       ▼
OrthoMCPClient (SSEClientTransport)
       │
       ▼    [HTTP http://localhost:8000/sse]
       │
FastMCP Server (memory-server)
       │
       ▼
Python (ortho-knowledge-graph)

We deliberately use Server-Sent Events (SSE) rather than standard stdio pipes. SSE is an HTTP-friendly transport layer that allows our Python memory server to run completely decoupled from the TypeScript orchestrator.

This decoupling is a massive architectural advantage. It means you can run your lightweight TypeScript orchestrator on a cheap serverless function (like AWS Lambda), while hosting your memory-intensive Python Knowledge Graph and Vector Databases on a dedicated, GPU-accelerated EC2 instance.

Automatic Tool Discovery#

The beauty of MCP is that the TypeScript orchestrator doesn't need to hardcode the Python tools. It discovers them dynamically.

When the OrthoWorkflow boots up, the OrthoMCPClient connects to the Python server and asks, "What can you do?"

typescript 
// packages/ortho-mcp-bridge/src/client.ts
public async connect(): Promise<void> {
    await this.client.connect(this.transport);
    
    // Automatic discovery!
    const { tools } = await this.client.listTools();
    this.toolsCache = tools;
    console.log(`[MCP Bridge] Discovered ${tools.length} knowledge graph tools.`);
}

The Python server responds with a standardized list of tools (insert_fact, find_path, record_decision), complete with their precise JSON Schema requirements and descriptions.

The OrthoMCPClient takes these definitions, wraps them into native TypeScript functions, and injects them seamlessly into the agent's prompt. The LLM has no idea it is talking to a Python server over HTTP; it just sees a tool called insert_fact and uses it natively.

The Ultimate Boundary: Security and Separation of Concerns#

Beyond convenience, MCP enforces a critical security boundary.

The TypeScript LLM agent is inherently untrustworthy. It is a stochastic text generator. We cannot trust it to manipulate database rows directly or execute raw SQL/Cypher queries.

By placing the MCP server in front of the Python Knowledge Graph, we create a strict API firewall. The LLM can only interact with the graph through the narrowly defined, heavily guarded MCP tools.

If the LLM wants to insert a fact, it must call insert_fact. The Python server intercepts this call, strips away any conversational fluff, and violently shoves the data through the four Knowledge Gates (Ontology, Identity, Provenance, Fusion). If the data fails a gate, the Python server returns a typed, deterministic error (e.g., PROV_O_VIOLATION) back over the MCP bridge. The LLM receives the error and must figure out how to fix its request.

The LLM never touches the database. It only talks to the bouncer.

Conclusion#

The Model Context Protocol is the glue that makes Graph Engineering possible at enterprise scale. It allows us to build polyglot, distributed AI systems where specialized components (orchestration, memory, reasoning) are loosely coupled but tightly integrated.

But there is one final security loophole we must close. We have given our agents access to powerful tools like resolve_conflict and merge_entities. What stops the lowly Executor agent from bypassing the Supervisor and approving its own data conflicts?

In Part 11: Cross-Language Capability Security (RBAC for Agents), we will explore how Orthograph OS implements a multi-layered, cryptographically secure Role-Based Access Control system that spans across both TypeScript and Python, ensuring that agents can never exceed their authority.
