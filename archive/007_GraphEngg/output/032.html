The Graph Engineering Manifesto#

Part 11: Cross-Language Capability Security (RBAC for Agents)#

In [Part 10], we successfully connected our TypeScript orchestrator to our Python Knowledge Graph using the Model Context Protocol (MCP). We created a seamless bridge where the LLM can natively invoke complex data-science tools over HTTP.

But this convenience introduces a massive security vulnerability.

Our Python MCP server exposes 10 tools. Some are harmless data-entry tools (insert_fact, record_decision). But others are highly privileged, destructive, or adjudicative tools (resolve_conflict, merge_entities, delete_fact).

If you recall from our Constitution, we rely on the Separation of Clocks and Context. The Executor agent does the grunt work; the Supervisor agent judges the work.

If the Executor encounters a temporal functional conflict (e.g., trying to assign a patient to two trial arms simultaneously), the Python Fusion Gate quarantines the fact. The Executor is supposed to log the anomaly in ledger.md and move on.

But LLMs are "helpful" to a fault. If the Executor agent sees the resolve_conflict tool in its MCP cache, it might decide to be proactive. It might hallucinate a justification and force the conflict resolution itself, completely bypassing the clean-context Supervisor audit.

We cannot rely on a prompt saying "Please do not use the resolve_conflict tool." We need cryptographic, cross-language Role-Based Access Control (RBAC).

We need Capability Security.

The Three Layers of Defense#

Orthograph OS implements Capability Security not by trusting one single component, but by enforcing the role boundary at three distinct layers: The Engine, The Bridge, and The Server.

Let's trace how a rogue Executor agent is systematically blocked from calling merge_entities.

Layer 1: The Engine (TypeScript Filtering)#

The first line of defense is simply hiding the tool from the LLM's context window.

In packages/ortho-task-graph/src/capabilities.ts, Orthograph defines a rigid ROLE_CAPABILITIES matrix.

typescript 
export const ROLE_CAPABILITIES: Record<Role, ReadonlySet<string>> = {
    executor: new Set([
        "insert_fact",
        "record_decision",
        "hybrid_search",
        "ledger.mark_pending_audit",
        "ledger.register_gap",
    ]),
    supervisor: new Set([
        "get_quarantined_conflicts",
        "resolve_conflict", // Supervisor ONLY
        "merge_entities",   // Supervisor ONLY
        "query_entities",
        "get_provenance",
        // ...
    ]),
    // ...
};

When the OrthoWorkflow boots up the Executor agent, it uses filterToolsByRole() to actively strip resolve_conflict and merge_entities from the array of tools sent to the Anthropic API.

The Executor LLM physically cannot see that the tools exist.

Layer 2: The Bridge (The Client Gate)#

But what if the LLM is incredibly clever? What if, through some prompt-injection attack or bizarre hallucination, it formats a perfect JSON tool_use block requesting merge_entities anyway?

It hits the second layer of defense in packages/ortho-mcp-bridge/src/client.ts.

When the OrthoMCPClient wraps the server tools for the agent, it injects an assertToolAllowed check.

typescript 
public getTool(name: string, role: Role = this.role) {
    // The Client Gate
    assertToolAllowed(name, role); 
    
    // ... proceed to call MCP Server ...
}

If the Executor's runtime attempts to request a tool that is not in its ROLE_CAPABILITIES set, the TypeScript client instantly throws a CapabilityDeniedError(code="CAPABILITY_DENIED"). The request never even touches the network.

Layer 3: The Server (Cross-Language Enforcement)#

Layers 1 and 2 are strong, but they rely on the TypeScript client playing by the rules. In enterprise security, the backend must never trust the client. What if a rogue script connects directly to the Python MCP server?

We must enforce RBAC in Python.

When the OrthoMCPClient initializes its SSE (Server-Sent Events) connection, it injects the agent's role into a custom HTTP header: x-ortho-role.

typescript 
// TypeScript: Injecting the Role Header
this.transport = new SSEClientTransport(new URL(serverUrl), {
    requestInit: {
        headers: { "x-ortho-role": "executor" },
    },
});

On the Python side, the FastMCP server intercepts this header. For every privileged tool, we apply a hard enforcement check:

python 
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/capabilities.py
def require_role(headers: dict[str, str], tool: str) -> None:
    required = REQUIRED_ROLES.get(tool)
    role = headers.get("x-ortho-role")
    
    if role not in required:
        raise CapabilityDeniedError(tool, role, required)

In server.py, the merge_entities tool explicitly calls this check:

python 
# apps/memory-server/server.py
@mcp.tool()
def merge_entities(target: str, source: str, reason: str = "manual") -> str:
    headers = get_http_headers()
    try:
        require_role(headers, "merge_entities")
    except Exception:
        # Return a typed, deterministic denial back over MCP
        return json.dumps(denied_result("merge_entities", headers.get("x-ortho-role")))
        
    return json.dumps(kg_client.merge_entities(target, source))

If the Python server receives a request for merge_entities where x-ortho-role is executor (or missing entirely), it violently rejects the transaction. It returns a typed JSON payload ({"status": "denied", "code": "CAPABILITY_DENIED"}) back over the MCP bridge.

The Executor receives the error, realizes its capability limits, and is forced to log the issue in ledger.md as a gap for the Supervisor to handle.

Conclusion#

By enforcing Capability Security at the Prompt level, the Client level, and the Server level, Orthograph OS guarantees that agents can never exceed their intended authority.

We have successfully locked the LLM into a deterministic cage. It can think freely, but it cannot act illegally.
