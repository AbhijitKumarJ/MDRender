The Graph Engineering Manifesto#

Part 5: Blocked ≠ Parked: Continuous Execution in Agentic Workflows#

In [Part 4], we explored how agents communicate through the Durable Edge—using tightly governed Markdown files (ledger.md, directives.md) to maintain state without bloated chat histories.

This file-based communication, combined with the Separation of Clocks (independent timers for the Executor and Supervisor), makes our system highly resilient. But it also introduces a massive operational challenge: Latency.

If the Executor finishes a major milestone and marks it pending-audit, it might have to wait 25 minutes for the Supervisor's slower clock to tick. If the Executor encounters a destructive action (like dropping a production database table) and marks it pending-owner-review, it might wait days for a human to wake up and approve it.

In a naive framework, the Executor just spins. It polls the ledger, realizes it is blocked, and goes back to sleep, wasting compute or doing absolutely nothing while waiting for permission to proceed.

In Orthograph OS, we enforce a strict operational law: Blocked ≠ Parked.

When the critical path is blocked, the agent must continue to generate value. Here is how we implement continuous execution in asynchronous agentic workflows.

The Pathology of "Side-Fixing"#

To understand how to keep an agent moving, we must first look at what not to do.

When a human developer is working on a feature and spots an unrelated bug, they often fix it "while they are in there." When an LLM does this, it is disastrous.

If an agent is tasked with migrating a database, and notices a typo in a CSS file, and decides to fix the CSS file, it pollutes the current Git diff. When the Supervisor wakes up to audit the "Database Migration," it sees a mess of unrelated CSS changes. The audit fails, the task is rejected, and the migration is delayed.

We solve this with a rigid rule: Register-then-Defer.

If the Executor spots a bug, an anomaly, or missing documentation mid-round, it is mathematically forbidden from fixing it. Instead, it must use the MCP tool ledger.register_gap to log the anomaly in the ledger.md's Debt & Gap Register.

markdown 
## Debt & Gap Register (Register-then-defer)
| ID      | Priority | Description                                       | Status |
| ------- | -------- | ------------------------------------------------- | ------ |
| GAP-001 | P2       | Found duplicate patient IDs across sites A and B. | open   |
| GAP-002 | P3       | Missing docstrings in authentication.py           | open   |

The Executor logs the gap and finishes its current, narrowly-defined slice of work.

The Gate-Wait Backlog (The Blocked-Work Lane)#

The Debt & Gap Register isn't just a burn-down list for the end of the project. It is the fuel that keeps the agent running during high-latency blocks.

Imagine Milestone 1 (Database Migration) is complete and marked pending-audit. The Executor is now technically blocked from advancing to Milestone 2.

Instead of going to sleep, the Orthograph kernel kicks the Executor into the Blocked-Work Lane. The Executor looks at the Debt & Gap Register and asks: "What can I do right now that won't ruin the Supervisor's audit?"

The Disjoint Write-Surface Algorithm#

It cannot just pick any gap. If the Executor decides to fix GAP-001 (Duplicate Patient IDs), it might modify the exact same database schemas that the Supervisor is currently trying to audit for Milestone 1.

To prevent this collision, Orthograph OS requires every task to declare its Write Surface.

markdown 
| ID       | Description               | Status        | Write Surface   |
| -------- | ------------------------- | ------------- | --------------- |
| ITEM-001 | Database Migration        | pending-audit | db-schemas      |

Before picking up a task from the Gap Register, the kernel calculates the mathematical intersection of the proposed task's write-surface against the write-surfaces of all pending-audit or blocked tasks.

typescript 
// packages/ortho-task-graph/src/ledger.ts
public getNextUnblockedItem(): LedgerItem | null {
    // 1. Find all surfaces currently locked by audits or human blocks
    const blockedSurfaces = new Set(
        this.items.filter(i => i.status === "blocked" || i.status === "pending-audit")
                  .flatMap(i => i.write_surface)
    );

    // 2. Find the highest priority gap whose write-surface is completely disjoint
    return this.gaps.find(gap => 
        gap.status === "open" && 
        !gap.write_surface.some(surface => blockedSurfaces.has(surface))
    ) || null;
}

Because GAP-002 (Missing docstrings in authentication.py) has a write-surface of auth-module, and the blocked milestone has a write-surface of db-schemas, the intersection is zero.

The Executor seamlessly picks up GAP-002, implements the docstrings, verifies the linter passes, and marks it closed—all while the Supervisor takes its time auditing the database migration.

Owner Escalations: A/B/C Cards, Not Homework#

Eventually, an agent will hit a task that a machine simply cannot authorize. For example: dropping a legacy database table, altering a production API contract, or lowering an accuracy threshold to pass a test.

Orthograph designates these as Red Lines. When the Executor hits a Red Line, it marks the task pending-owner-review and moves to the Blocked-Work Lane.

But how it escalates to the human owner is critical.

In 2024, agents would dump a massive technical log into the chat UI: "I encountered an error trying to drop the table because of a foreign key constraint on the users table. Here is the stack trace..."

The human owner, who hasn't looked at the code in three days, is suddenly forced to reconstruct the agent's entire context, debug the SQL, and write a detailed prompt to fix it. This is exhausting. It turns the human into the agent's assistant.

In Graph Engineering, escalations are treated as an API contract. The agent is forced to format its block as an Owner Choice Card. It must investigate the issue, formulate the tradeoffs, and present the human with a maximum of three mutually exclusive choices.

text 
Decision needed: The old photo-data column still exists. We have verified all 4,812 photos are successfully migrated to AWS S3. Should we drop the legacy column?
Why now: M3 cannot finish while both storage copies remain active.
Recommendation: A — Drop the column now (safest path forward, data is verified).
A (Recommended) — Drop it using a reversible migration script.
B — Keep the column for one release cycle as a hot-backup, drop later.
Reply with: A / B

The owner does not need to read code. They read the card, reply A, and the agent translates that intent into the necessary technical execution on its next tick.

Conclusion#

By enforcing Register-then-Defer, calculating Disjoint Write-Surfaces, and utilizing A/B/C Choice Cards, Orthograph transforms blocking events from system-halting failures into smooth, asynchronous lane-changes. The agent is always adding value, and the human is never burdened with context reconstruction.

We have now conquered the execution half of Graph Engineering (The Task Graph). Our agents run safely, efficiently, and endlessly.

But an agent is only as good as the facts it bases its decisions on.
