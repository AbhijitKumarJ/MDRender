# The Graph Engineering Manifesto

## Part 13: Revision-Bound Audits: Solving Agent Race Conditions

In [Part 12], we looked at how Orthograph OS protects its state on disk. Using atomic writes (`tmp → fsync → rename`) and the Projection Pattern, we ensured that a server crash or an LLM hallucination could never corrupt the `ledger.md`.

But physical disk corruption is only half the battle. When you have multiple autonomous agents running concurrently on independent timers, you face a much more insidious threat: **Logical Race Conditions.**

In this post, we will explore the "Stale Accept" problem, and how the Orthograph kernel uses **Monotonic Revisions** and **Revision-Bound Audits** to guarantee absolute synchronization between the Executor and the Supervisor.

---

### The "Stale Accept" Vulnerability

Let’s visualize a standard timeline in a naive multi-agent framework.

1.  **10:00 AM:** The Executor finishes writing a database migration script. It marks `ITEM-001` as `pending-audit`.
2.  **10:05 AM:** The Supervisor wakes up. It begins its cold-read audit. It downloads the Git diff, analyzes the migration script, and begins writing its detailed evaluation. (This is a heavy LLM call that might take 60 seconds).
3.  **10:05:30 AM:** While the Supervisor is "thinking," the Executor wakes up on its fast timer. The Executor realizes it made a typo in the migration script. It quickly patches the file, commits the fix, and goes back to sleep.
4.  **10:06 AM:** The Supervisor finishes its evaluation. Based on the *original* (flawless) code it read at 10:05, it decides the task is perfect. It issues the command to mark `ITEM-001` as `closed`.

**The system has just suffered a catastrophic logical failure.** 

The Supervisor approved the code at `10:05:00`. The codebase currently reflects the state at `10:05:30`. The Supervisor has officially stamped its approval on code it *has never actually read*. If the Executor's quick typo-fix actually introduced a severe SQL injection vulnerability, that vulnerability was just pushed to production with the Supervisor's seal of approval.

In a framework relying on fuzzy LLM orchestration, this race condition is almost impossible to catch until it destroys production data.

### The Solution: Monotonic Revisions

Orthograph OS solves this by treating the task ledger exactly like a modern distributed database.

Every time *any* mutation happens to the ledger—whether the Executor registers a gap, marks an item pending, or updates a convergence tracker—the kernel increments a global, monotonic `revision` integer.

```json
// state.json
{
  "header": {
    "runStatus": "active",
    "milestone": "M1",
    "revision": 17 // <-- The heartbeat of the graph
  }
}
```

This `revision` number is deeply integrated into the `LedgerCommandHandler`.

### The Two-Step Audit Protocol

When the Supervisor decides to approve a task, it cannot simply command the kernel to close the item. Approval in Orthograph is a rigorous, cryptographically verifiable two-step process.

#### Step 1: Submitting the Audit Record
First, the Supervisor must call the MCP tool `audit.submit`. It provides its decision (`accept`), its reasoning, and the specific deterministic checks it ran.

The kernel intercepts this call and creates an immutable `AuditRecord`. Crucially, **the kernel stamps the AuditRecord with the exact ledger revision that existed at the exact millisecond the audit was submitted.**

```typescript
// packages/ortho-task-graph/src/command-handler.ts
const record: AuditRecord = {
    auditId: `AUDIT-${Date.now()}-${itemId}`,
    auditorId: "supervisor",
    decision: "accept",
    // ... evidence and checks ...
    ledgerRevision: handler.revision, // <-- Binding the audit to the timeline
};
audits.append(record);
```

The tool returns the `auditId` back to the Supervisor LLM.

#### Step 2: Proposing the Closure
Now, the Supervisor calls `ledger.mark_closed`, passing in the `itemId` and the `auditId` it just generated.

This is where the magic happens. The `LedgerCommandHandler` executes the `requireAudit` validation logic before allowing the state transition.

```typescript
// packages/ortho-task-graph/src/command-handler.ts
private requireAudit(itemId: string, auditId: string): void {
    const audit = this.audits.get(auditId);
    
    // ... verify audit exists, targets the right item, and says "accept" ...

    if (audit.ledgerRevision !== this.ledger.getHeader().revision) {
        throw new LedgerAuditError(
            "STALE_REVISION",
            `audit '${auditId}' verified revision ${audit.ledgerRevision} but the ledger is now at ` +
            `${this.ledger.getHeader().revision}; re-audit before closing.`
        );
    }
}
```

Let's apply this to our earlier scenario. 

1.  At 10:00 AM, the Executor marked the item pending (Revision 16).
2.  At 10:05 AM, the Supervisor began its audit.
3.  At 10:05:30 AM, the Executor patched the code and updated the ledger (Revision 17).
4.  At 10:06 AM, the Supervisor calls `audit.submit`. The kernel records `AUDIT-123` tied to **Revision 17**. 

Wait, why did the kernel record Revision 17 if the Supervisor *read* the data at Revision 16?

Because the Supervisor's tool call arrived *after* the Executor's mutation. The kernel evaluates the state at the exact moment of the command. 

When the Supervisor calls `ledger.mark_closed(auditId="AUDIT-123")`, the kernel checks the audit's recorded revision (17) against the current ledger revision (17). **Wait, this passes!**

*Correction: Let's look closely at how Orthograph actually handles this.*

The Supervisor LLM reads `ledger.md` at 10:05. It sees Revision 16. It does its thinking. 
At 10:05:30, the Executor mutates the ledger. The kernel bumps the ledger to **Revision 17**.
At 10:06, the Supervisor calls `audit.submit`. 

In the current Orthograph implementation, the `audit.submit` tool *automatically* grabs the current `handler.revision` (which is now 17) and stamps it on the audit. Then `mark_closed` checks if `audit.ledgerRevision` (17) equals `handler.revision` (17). This would pass, which is a flaw!

**The True Orthograph Fix:**
To truly prevent the Stale Accept, the Supervisor must *declare* which revision it audited when it submits the audit. 

The prompt must say: *"When calling `audit.submit`, you must provide the `revision` number you read from the Status Header of `ledger.md`."*

Then, the kernel logic becomes:

```typescript
// Proposed Kernel Logic
execute(args) {
    const claimedRevision = args.revision_read_by_supervisor;
    if (claimedRevision !== handler.revision) {
         throw new LedgerAuditError("STALE_REVISION", "The ledger mutated while you were auditing. Re-read and re-audit.");
    }
    // ... append AuditRecord ...
}
```

*Author's Note: The code provided in the blueprint automatically stamps the `handler.revision` during `audit.submit`, which technically allows the race condition if the mutation happens between the read and the submit. To achieve perfect strictness, the LLM must pass the revision it read as an argument to the MCP tool.*

However, assuming the strict revision-passing is implemented, the result is beautiful. If the Executor mutates the state, the revision bumps to 17. The Supervisor submits its audit claiming it verified Revision 16. The kernel throws `STALE_REVISION`. The task is not closed. The Supervisor is forced to pull the new data, re-evaluate the typo-fix, and issue a fresh audit.
