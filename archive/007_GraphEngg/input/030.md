# The Graph Engineering Manifesto

## Part 9: Decisions are Nodes: Making AI Reasoning Legally Auditable

In [Part 8], we finalized the defenses of our Knowledge Graph. With Ontology, Provenance, Identity, and Fusion gates in place, we can guarantee that every piece of data inside `ortho-knowledge-graph` is structurally sound, conflict-free, and cryptographically linked to a trusted source document. 

We have successfully modeled the *reality* of the enterprise. But in 2026, storing data isn't enough. We must also store the *reasoning* applied to that data.

### The Ephemeral Thought Problem

When an autonomous agent performs a complex task—like reviewing a patient's medical history to determine clinical trial eligibility—it relies on Chain-of-Thought reasoning. It pulls in facts, weighs them against constraints, and reaches a conclusion.

In early agent frameworks, this brilliant logical deduction lived entirely inside the LLM's context window. When the agent finished its task and shut down, that context window vanished into the ether. The only thing left was the final output (e.g., an updated database row saying `Eligible: False`).

If an auditor, a regulator, or a human doctor later asks, *"Why was this patient rejected?"* the answer is gone. The context is destroyed. The engineers can only point to the final output and say, *"The AI decided."*

This is the ultimate failure of AI governance. If you cannot produce the exact logical chain that led to a decision, you cannot deploy AI in a regulated environment.

### Decision Intelligence: Turning Logic into Topology

In Graph Engineering, we solve this by promoting an agent's reasoning from ephemeral text to durable, topological mathematics. We call this **Decision Intelligence**.

In Orthograph OS, a decision is not a log entry. It is a first-class node in the Knowledge Graph.

When the Executor agent finishes analyzing a patient, it does not just update the `ledger.md`. It is required to call a specific MCP tool: `record_decision`.

```json
// The Executor's MCP Tool Call
{
  "tool": "record_decision",
  "arguments": {
    "agent_id": "executor-haiku-v4",
    "conclusion": "Patient p-001 is ineligible for Trial Arm A due to a reported severe cardiac arrhythmia.",
    "supporting_fact_ids": ["fact-18b44093", "fact-41ffd800"]
  }
}
```

This tool call instructs the Python kernel to create a brand new node of type `AgentDecision` and establish hard, directed edges to the specific facts the agent cited.

### The "Dangling Reference" Gate

However, we know from our Constitution that we cannot trust the LLM. What if the agent hallucinated a `fact_id` that doesn't exist? What if it tries to justify its decision using data it just made up?

The Orthograph kernel enforces strict referential integrity.


If the agent cites a non-existent fact, the kernel violently rejects the transaction with a `DANGLING_FACT_REF` error. The decision is not saved. The agent is forced to try again, this time citing real, provenance-backed data.

### The Cryptographic Audit Trail

Once the decision passes the gate, the kernel doesn't just save the node; it mathematically seals it. 

It generates a `decision_hash`—a SHA-256 fingerprint that binds the agent ID, the exact text of the conclusion, the timestamp, and the sorted list of `supporting_fact_ids`. 

```python
decision_hash = compute_decision_hash(
    agent_id, conclusion, supporting_fact_ids, timestamp
)
```

Because the cited facts *also* have cryptographic hashes (`fact_hash`) linking them to their source documents via PROV-O, we have created an unbroken, immutable chain of accountability.

### The `trace_decision_chain` Query

This architecture enables the ultimate compliance tool.

If a regulator challenges a decision six months later, you do not need to guess what the AI was thinking. You use the `trace_decision_chain(decision_id)` API.

This function traverses the graph backward:
1.  **The Decision Node:** It shows the exact conclusion ("Patient ineligible...") and the cryptographic signature of the agent model that made it.
2.  **The Facts:** It follows the edges to the specific `Fact` nodes (e.g., `Patient -> REPORTED_EVENT -> Arrhythmia`).
3.  **The Extraction:** It follows the PROV-O lineage to the exact millisecond the fact was extracted from raw text.
4.  **The Source Document:** It follows the lineage to the specific chunk of `trial_data_v2.csv` that contained the original data.

You have a complete, machine-auditable, cryptographically secure proof of reasoning, from the raw data all the way to the final conclusion.
