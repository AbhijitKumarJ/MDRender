# The Graph Engineering Manifesto

## Part 14: Anatomy of Orthograph: The Python Semantic Engine

Throughout the first thirteen parts of this series, we have focused heavily on the **Task Graph** (`ortho-task-graph`). We explored how the TypeScript orchestrator acts as an unyielding kernel, enforcing the "Separation of Clocks," ensuring atomic filesystem writes, and using monotonic revisions to prevent multi-agent race conditions.

But perfect orchestration is meaningless if the data the agents are manipulating is corrupt, hallucinated, or contradictory.

In Graph Engineering, execution logic and memory management are fundamentally different problem domains, requiring different architectures and different languages. Today, we cross the Model Context Protocol (MCP) bridge into the second half of Orthograph OS: **The Knowledge Graph** (`ortho-knowledge-graph`).

Written in Python, this semantic engine acts as a rigorous data-science firewall. It guarantees that every piece of knowledge stored by the agents is structurally sound, mathematically fused, and cryptographically provenanced.

Let’s dissect the four gates of the Python Semantic Engine.

---

### The Ingestion Pipeline: `insert_fact`

The core entry point for any data into Orthograph’s memory is the `insert_fact` MCP tool. 

When an agent (like the Executor) reads a document and wants to store a relationship—for instance, noting that Patient P-001 reported an adverse event—it invokes `insert_fact`.

```json
// The Agent's MCP Tool Call
{
  "tool": "insert_fact",
  "arguments": {
    "subject_id": "p-001",
    "subject_type": "PatientRecord",
    "relation": "REPORTED_EVENT",
    "obj_id": "ae-001",
    "obj_type": "AdverseEvent",
    "source_doc": "trial_data_v2",
    "agent_id": "executor-haiku-v4"
  }
}
```

In a naive vector database, this JSON payload would simply be embedded and appended to a table. In Orthograph, this payload must survive a gauntlet of four deterministic Python gates.

### Gate 1: The Ontology Gate

The very first check ensures the agent isn’t hallucinating relationships that don't make logical sense in our business domain.

```python
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/store/client.py (simplified)

# 1. Ontology Gate
check = self.schema.check_triplet(subject_type, relation, object_type)
if not check["ok"]:
    return {"status": "rejected", "code": "ONTOLOGY_VIOLATION", "reason": check["reason"]}
```

The `GraphSchema` class holds the defined rules of our reality. We explicitly defined that the `REPORTED_EVENT` relation requires a domain of `PatientRecord` and a range of `AdverseEvent`. If the LLM got confused and tried to assert that a `[Doctor] -> (REPORTED_EVENT) -> [AdverseEvent]`, this gate intercepts it.

It returns a typed JSON response (`ONTOLOGY_VIOLATION`) back over the MCP bridge. The LLM sees the rejection and must correct its extraction logic. The database remains unpolluted.

### Gate 2: The Provenance Gate

Even if the relationship is logically valid, we must prove it actually came from the source text.

```python
# 2. Provenance Gate
if not self.provenance.verify_source(prov_doc):
    return {
        "status": "rejected",
        "code": "PROV_O_VIOLATION",
        "reason": f"Source document '{prov_doc}' is not registered..."
    }
```

The `DocumentRegistry` maintains the "Trusted Corpus." If the LLM tries to justify the adverse event by citing a document ID it just invented (e.g., `source_doc: "doctor_notes_xyz"`), the `ProvenanceTracker` flags it as a hallucination.

If the document *is* valid, the tracker generates an immutable W3C PROV-O lineage tag. It computes a cryptographic SHA-256 hash (`extraction_hash`) that permanently binds the agent's ID, the document ID, the timestamp, and the specific chunk index together.

### Gate 3: The Identity Gate (Entity Fusion)

LLMs are notoriously inconsistent with nomenclature. In one document, it might extract the entity `"Southeast University"`. In another document, it might extract `"SEU"`. 

If we store both as separate nodes, multi-hop graph queries (like "Find all patients enrolled at Southeast University") will silently fail, because half the patients are linked to the "SEU" node.

The Identity Gate solves this deterministically.

```python
# 3. Identity Gate
subject_id = self._canonical(subject, agent_id)
obj_id = self._canonical(obj, agent_id)
```

The `EntityRegistry` intercepts the incoming entity labels. If it detects an exact alias match, it automatically performs a **Fusion Event**. It merges the incoming node into the existing canonical node, re-routes all incoming and outgoing edges, and creates an audited merge log entry. 

To the rest of the graph, "SEU" and "Southeast University" are now mathematically identical.

### Gate 4: The Fusion Gate (Temporal Conflicts)

The final gate handles the hardest problem in semantic memory: Contradiction.

In our schema, we defined the `ASSIGNED_ARM` relationship as `functional=True`. A patient can only be assigned to *one* trial arm at a time. 

If the agent tries to ingest a fact stating Patient P-001 is in "Trial Arm B", but the graph already shows P-001 in "Trial Arm A", the `SemanticConflictQueue` activates.

```python
# 4. Fusion Gate
conflict = self.fusion.check_functional_violation(new_triplet, existing_triplets, is_functional)
if conflict:
    self.store.quarantine_conflict(self.fusion.quarantine[-1])
    return {
        "status": "quarantined",
        "code": "FUSION_CONFLICT",
        "reason": "Fact conflicts with an existing functional relation..."
    }
```

Instead of crashing or silently overwriting the old data, the engine quarantines the new fact. It returns a `quarantined` status to the Executor agent. 

The Executor logs the anomaly in its `ledger.md` (Register-then-Defer) and moves on. Later, the Supervisor agent (which possesses the privileged `resolve_conflict` MCP tool capability) will query the quarantine queue, evaluate the conflicting evidence, and definitively adjudicate whether Trial Arm A or Trial Arm B is the correct reality.

### Conclusion

The Python Semantic Engine is not a database wrapper; it is an active, aggressive firewall. By forcing every single fact through Ontology, Provenance, Identity, and Fusion gates, Orthograph guarantees that its memory is enterprise-grade, legally auditable, and structurally perfect.

But where does this perfect data actually live? In our development environment, it lives in a simple JSON file. For production, we need something much more powerful.
