# The Graph Engineering Manifesto

## Part 16: Hybrid GraphRAG: Blending Vectors with Topological Math

In [Part 15], we moved our semantic memory from a simple JSON file into a production-grade Triple Store using Oxigraph and RDF 1.2 Reifiers. We now have a massive, highly efficient, and deeply interlinked Knowledge Graph. 

We can write blazing-fast SPARQL queries to traverse this topology. We can ask: *"Find the shortest path between `Patient-4012` and the `AdverseEvent-88`."* 

But there is a catch. 

To run a topological query, the agent must know the exact `Entity ID` of the starting node. If the agent asks for the path from "Alice" to "Arrhythmia," the graph database will return an empty result, because it only understands the IDs `p-001` and `ae-001`.

In early agent frameworks, developers tried to solve this by dumping the entire schema or a list of all entity names into the LLM's prompt window. At enterprise scale—with millions of entities—this immediately crashes the context window.

Agents need to search by *meaning*, but traverse by *math*. To achieve this, Orthograph OS implements **Hybrid GraphRAG**.

### The Two Steps of Hybrid Retrieval

Orthograph bridges the gap between human language and graph topology by providing the agents with a new MCP tool: `hybrid_search`. 

When an agent needs to investigate a topic but doesn't know the exact IDs, it calls the search tool with a natural language query:

```json
{
  "tool": "hybrid_search",
  "arguments": {
    "query": "university research hospitals",
    "limit": 5
  }
}
```

Behind the scenes, Orthograph executes a two-step retrieval process.

#### Step 1: Lexical Gating (The Fast Filter)
Vector search (cosine similarity) is powerful, but it is notoriously prone to retrieving "noise"—documents that share a mathematical vector space but are completely unrelated in topic. 

Orthograph solves this by applying a **Lexical Overlap Gate** *before* running the math. It tokenizes the query (`["university", "research", "hospitals"]`) and checks it against the tokens of the entities in the database. If an entity doesn't share at least one actual keyword with the query, it is immediately discarded. This prevents a search for "cancer drug trial" from erroneously returning a node about a "weather forecast report."

#### Step 2: Deterministic Vector Embedding (The Hashing Trick)
Once the noisy candidates are filtered out, Orthograph needs to rank the remaining entities by semantic similarity.

Usually, this requires importing massive PyTorch models, running transformer inference on a GPU, and storing the results in a heavy database like Pinecone or Milvus. 

Orthograph rejects this bloat. To keep the core framework ultra-fast, deterministic, and dependency-free, we use a classic data-science technique: **The Hashing Trick**.

```python
# packages/ortho-knowledge-graph/src/ortho_knowledge_graph/vector/embed.py
def hash_embed(
    text: str, dim: int = 128, min_ngram: int = 2, max_ngram: int = 3
) -> list[float]:
    """Deterministic offline embedding via the hashing trick."""
    vec = [0.0] * dim
    
    # 1. Break text into tokens and n-grams
    tokens = extract_ngrams(text)
    
    # 2. Hash each token using SHA-256 (not Python's built-in hash())
    for token in tokens:
        digest = int.from_bytes(hashlib.sha256(token.encode("utf-8")).digest()[:8], "big")
        
        # 3. Project into the fixed-size vector space
        vec[digest % dim] += 1.0 if (digest >> 63) & 1 else -1.0
        
    # 4. Normalize the vector
    return normalize(vec)
```

Instead of a neural network, we use a cryptographic hash (SHA-256) to project character n-grams into a fixed 128-dimensional vector space. 

This approach has three massive advantages for an AI orchestrator:
1.  **Zero Dependencies:** It runs in pure Python. No GPUs, no massive `.bin` model files to download.
2.  **Blazing Fast:** Generating embeddings for millions of entity labels takes seconds, not hours.
3.  **100% Deterministic:** Because we use SHA-256 instead of Python's built-in `hash()` (which is randomly salted on every execution), two different servers will *always* generate the exact same vector for the same text. If a server crashes, the index can be perfectly rebuilt from the database without any drift.

### The Agentic Workflow: Search → Traverse → Conclude

With the `hybrid_search` tool enabled, the Executor agent now has a complete GraphRAG workflow. 

1.  **Search:** The agent encounters a note about "Southeast Univ." It doesn't know the ID. It calls `hybrid_search(query="Southeast Univ")`.
2.  **Resolve:** The tool returns a JSON array containing `[{"entity_id": "org-hybrid", "label": "Southeast University Research Hospital", "score": 0.89}]`.
3.  **Traverse:** The agent now knows the exact ID. It calls the `neighbors(entity_id="org-hybrid")` or `find_path(start="org-hybrid", end="ae-001")` MCP tools to execute deep, deterministic topological queries. 
4.  **Conclude:** The agent analyzes the returned subgraph, reaches a conclusion, and calls `record_decision()`—permanently logging its findings back into the database with cryptographic PROV-O lineage.
