# The Graph Engineering Manifesto

## Part 4: The Durable Edge: Filesystems as Agent APIs

In [Part 3], we established the necessity of the **Clean-Context Supervisor** and the "Separation of Clocks." Our Executor and Supervisor run on entirely independent timers and boot with clean, isolated context windows. 

But this raises a practical problem: If these agents don't share a session, don't talk over a REST API, and don't maintain a continuous chat history, **how do they communicate?**

In 2024, frameworks tried to solve this with complex "Agent-to-Agent" messaging buses, passing massive JSON payloads back and forth. It was brittle, difficult to debug, and prone to losing context.

In Graph Engineering, we use the simplest, most robust interface available to a computer: **The Filesystem.** 

Agents communicate *only* by reading and writing durable Markdown files. We call this pattern the **Durable Edge**.

---

### Why Markdown? (The API for Both Silicon and Carbon)

Why use files like `ledger.md` and `directives.md` instead of a hidden SQLite database or an in-memory Redis cache?

Because an autonomous agent's state must be equally legible to a Large Language Model and a human engineer.

When an agent goes off the rails at 3:00 AM, you do not want to be querying a proprietary database or parsing raw JSON message queues to figure out what it was thinking. You want to open `ledger.md` in VS Code, read a perfectly formatted markdown table that says exactly what task failed, and see the exact instructions the Supervisor issued in `directives.md`.

Markdown is the ultimate dual-purpose API. LLMs are natively trained on vast amounts of Markdown; they understand its structure (tables, headers, lists) flawlessly. Humans can read, diff, and manually edit it without special tooling.

If the agent is stuck, you can literally open `directives.md`, type a new instruction yourself, save the file, and the agent will pick it up on its next clock tick. You are just another node in the graph.

### The Two Edges: State vs. Signal

In Orthograph OS, we utilize two distinct types of durable file edges, governed by strict read/write discipline.

#### 1. The State Edge: `ledger.md` (The Scoreboard)
*   **Discipline:** Single-Writer, In-Place Rewrite.
*   **Writer:** The Executor.
*   **Reader:** The Supervisor (Read-Only).

The ledger is the single source of truth for the run. It contains the goal, the active milestones, the "Gate Scoreboard" (which tests must pass), and the "Debt & Gap Register" (where the agent logs anomalies).

Crucially, the Executor does not *append* to the ledger infinitely. It uses MCP tools to rewrite the ledger *in place*. It changes a task from `open` to `pending-audit`, updating a single row in a markdown table. This prevents the file from becoming a sprawling history log.

#### 2. The Signal Edge: `directives.md` (The Queue)
*   **Discipline:** Single-Writer, Append-Only Queue, Consume-and-Archive.
*   **Writer:** The Supervisor (or the Human Owner).
*   **Reader:** The Executor.

`directives.md` is how the Supervisor steers the Executor. It is an ordered, one-way queue of corrections (e.g., `"D-014: Redo task 2. You forgot to sanitize the PII."`). 

### The Token Economics of State: Preventing Context Collapse

Here is the central challenge of file-based memory: **Context windows are expensive, and attention degrades as prompts get longer.** 

If you just let agents append to files forever, by round 100, `ledger.md` will be 80,000 tokens long. The agent will slow to a crawl, your API bills will skyrocket, and the LLM will start missing critical instructions buried in the noise ("Lost in the Middle" syndrome).

Graph Engineering requires that **every durable section is strictly bounded by a cap.**

#### 1. Archiving (The Watermark Pattern)
When the Executor reads a directive from the Supervisor (e.g., `D-014`) and successfully applies the correction, it does not leave `D-014` in the active `directives.md` file. 

Instead, Orthograph enforces a **Consume-and-Archive** pattern. The system automatically moves consumed directives into `.orthograph/archive/directives-archive.md`. 

The active `directives.md` file is a *Live Queue*, capped at a maximum of 8 items. The Executor only ever reads the live queue. Cold history goes to the archive, ensuring the active context window remains aggressively small and hyper-focused.

#### 2. Forced Convergence (The Brake Pedal)
Agents love to add code, add features, and add complexity. They hate deleting things. If left unchecked, they will inflate a codebase until they can no longer reason about it.

Orthograph introduces a mechanical forcing function: **The Convergence Round**.

In the `ledger.md`, the system tracks two metrics: `rounds_since_convergence` and `net_lines_since_convergence`. 

```markdown
Convergence tracker: rounds since last 5: **4** | net lines since last +400: **+120** | **next round converges: yes**
```

When either counter hits its cap (e.g., 5 rounds or +400 net-new lines of code), the system flags a Convergence Round. 

During this round, the Executor's prompt changes. **It is explicitly forbidden from adding new features.** Its sole job is to delete dead code, merge duplicate functions, tighten interfaces, and compress the `ledger.md` file itself. Its net-lines output must be $\le 0$. 

This is not a polite suggestion. Because this flag is tracked in the durable `ledger.md`, the stateless Executor is forced to see it on its next boot. The Supervisor explicitly audits that the Convergence Round took place and resulted in code reduction.

### Conclusion

By using the filesystem as our API, we achieve total observability. By enforcing strict caps, archives, and forced convergence, we ensure our agents stay cheap, fast, and focused.

But what happens when an agent hits a wall? What if it needs a human to provide an API key, or it's waiting for the Supervisor to audit a massive database migration? Does the whole system just stop and waste compute?
