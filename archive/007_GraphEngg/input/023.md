# The Graph Engineering Manifesto

## Part 2: Stop Letting LLMs Control State: The Case for Deterministic Kernels

In [Part 1], we diagnosed the fatal disease of 2024-era AI architecture: **Context Poisoning**. We established that placing an LLM in an open-ended `while(true)` loop inevitably leads to scope creep, hallucinated progress, and catastrophic drift. 

The cure for this is **Graph Engineering**, which rests on a single, non-negotiable maxim: *Keep the LLM fuzzy, but make the infrastructure rigid.*

Today, we are going to implement that maxim. We are going to look at the heart of **Orthograph OS**, and we are going to strip the LLM of its most dangerous power: the ability to control state.

---

### The Fundamental Flaw of "Prompt-Driven" Orchestration

Look at a typical early-era agent framework. The orchestration usually relies on a system prompt that looks something like this:

> *“You are an autonomous agent. When you finish a task, respond with a JSON object: `{"status": "complete"}`. If you need a human, respond with `{"status": "escalate"}`.”*

In this design, the LLM is running the application logic. The python or typescript wrapper is just a dumb pipe waiting for the LLM to dictate control flow. 

This is a profound architectural mistake. 

LLMs are probabilistic text generators. They are not state machines. When an LLM gets confused, distracted, or encounters an edge case, it will happily invent new statuses (`{"status": "almost_done"}`), bypass required approval steps, or prematurely mark a failing task as `complete`.

When you rely on prompts to enforce state, you are asking a stochastic engine to behave deterministically.

### "Code is the Plan": Enter the Deterministic Kernel

In Graph Engineering, **Code is the plan**. 

In Orthograph OS, branching, looping, halting, and state transitions live in strict, mathematically sound code (TypeScript). The LLM is relegated to a highly restricted "reasoning engine" component that can only *propose* actions.

We achieve this by implementing a **Deterministic Kernel**. 

Instead of an LLM freely editing a file or changing a database flag, it must submit a typed command to a `CommandHandler`. The kernel sits between the LLM and the database, acting as an unyielding bouncer.

Let's look at how this is enforced in the `ortho-task-graph` package.

### The Command Pattern for Agents

In Orthograph, an agent can never say, *"I am done, mark the task closed."* 

Instead, the agent is provided with an MCP (Model Context Protocol) tool. When the Executor agent thinks it has finished a task, it invokes the tool `ledger.mark_pending_audit`.

This tool call generates a typed `LedgerCommand`:

```typescript
// packages/ortho-task-graph/src/commands.ts
export type LedgerCommand =
    | { type: "mark-pending-audit"; itemId: string; evidence?: string; commandId?: string }
    | { type: "mark-blocked"; itemId: string; commandId?: string }
    | { type: "mark-closed"; itemId: string; auditId: string; commandId?: string }
    | { type: "reopen"; itemId: string; reason: string; commandId?: string }
    | { type: "register-gap"; priority: string; description: string; commandId?: string };
```

Notice what is missing from this list. There is no generic `update_status` command. There is no `force_close`. The options are strictly bounded.

### The Bouncer: `LedgerCommandHandler`

When the agent proposes a command, it is intercepted by the `LedgerCommandHandler`. This is the kernel. It does not care what the LLM's prompt said; it only cares about the laws of the system.

First, it checks **Authorization (RBAC)**. 

```typescript
// packages/ortho-task-graph/src/commands.ts
export const COMMAND_AUTHORIZATION: Record<Role, ReadonlySet<LedgerCommand["type"]>> = {
    executor: new Set(["mark-pending-audit", "register-gap"]),
    supervisor: new Set(["mark-closed", "reopen", "mark-blocked"]),
    kernel: new Set([...]) // Internal system commands
};
```

If the Executor agent tries to call `mark-closed`, the kernel instantly rejects the transaction with a `UNAUTHORIZED` error. The Executor simply does not have the cryptographic capability to close a task. It can only submit it for audit.

Second, it checks **State Machine Validity**.

```typescript
// packages/ortho-task-graph/src/ledger.ts
const TRANSITIONS: Record<LedgerStatus, Partial<Record<LedgerStatus, true>>> = {
    open: { "pending-audit": true, blocked: true },
    "pending-audit": { closed: true, open: true },
    blocked: { open: true },
    closed: { open: true },
};
```

If a task is currently `open`, and an agent tries to jump straight to `closed`, the kernel throws an `ILLEGAL_TRANSITION` error. 

### Why This Architecture Wins

By moving control flow out of the prompt and into a Deterministic Kernel, we achieve three critical enterprise guarantees:

1. **Provable Compliance:** We no longer have to "hope" the LLM follows the rules. We can write unit tests asserting that unauthorized state transitions are mathematically impossible.
2. **Graceful Error Handling:** If the LLM makes a mistake (e.g., trying an illegal transition), the kernel doesn't crash. It returns a typed, deterministic error (`{ok: false, code: "ILLEGAL_TRANSITION", reason: ...}`). The LLM can read this error and attempt to correct its behavior, but no data is corrupted.
3. **Idempotency and Replayability:** Because every state change goes through a command handler, we can require a `commandId`. If a server crashes mid-tick and restarts, re-playing the exact same `commandId` results in a safe, deduplicated no-op.

### What's Next?

We have successfully locked down state transitions. We have ensured that the Executor agent can only *propose* that a task is finished (`pending-audit`). 

But who actually approves that task? If the Executor can't close it, someone else must.
